# warsaw-self-signed-rest-api — Design

**Date:** 2026-08-07
**Status:** Approved for planning

## Goal

A REST API that authenticates a single machine client with OAuth 2.0 `private_key_jwt`
(RFC 7523 §2.2), issues its own RS256-signed access tokens, publishes the verification key
as a JWKS, and enqueues authenticated request bodies onto a shared SQS queue.

Warsaw is modelled on `helsinki-api-gateway-rest-api` and keeps its shape: one Lambda behind
an API Gateway REST API, `mb-config` for layered configuration, Powertools for logging and
metrics, deployment split into small CloudFormation stacks driven by GitHub Actions.

The one substantive departure is authentication. Helsinki takes a `client_secret` and signs
tokens with a shared HMAC secret. Warsaw takes a client-signed JWT assertion and signs tokens
with its own RSA private key — no shared secret exists anywhere in the system.

## Non-goals

- No consumer Lambda and no queue stack. Warsaw is a pure producer against the existing
  shared oslo queue, exactly as helsinki is.
- No multi-client registry, no `kid`-based client key selection, no per-client rotation.
  One client, one public key.
- No `jti` replay tracking. That needs a DynamoDB table with a TTL; see "Replay" below for
  what is done instead.
- No refresh tokens, no token introspection, no revocation.
- No dynamic client registration or discovery document beyond the JWKS endpoint.

## Request flow

```
                    ┌──────────────────────────────────────────┐
                    │ API Gateway REST API (regional)          │
   client ─────────▶│ resource policy: deny unless source IP   │
                    │ ∈ SSM /allowed-ips/all                   │
                    └───────────────────┬──────────────────────┘
                                        │ ANY / and /{proxy+}
                                        ▼
                    ┌──────────────────────────────────────────┐
                    │ Lambda  app.main.lambda_handler          │
                    │ APIGatewayRestResolver                   │
                    ├──────────────────────────────────────────┤
                    │ POST /oauth/token   → app/oauth.py       │
                    │ GET  /.well-known/jwks.json → app/jwks.py│
                    │ POST /              → app/producer.py    │
                    └───────────────────┬──────────────────────┘
                                        │ SendMessage
                                        ▼
                              shared oslo SQS queue
```

Two-step client interaction:

1. `POST /oauth/token` with a `client_assertion` signed by the client's private key.
   Warsaw verifies it against the committed client public key and returns an RS256 access token.
2. `POST /` with `Authorization: Bearer <access token>`. Middleware verifies the token against
   warsaw's own public key, then the body is enqueued.

## Key model

Two independent RSA keypairs. Neither private key is ever committed.

| Key | Generated by | Lives in | Purpose |
| --- | --- | --- | --- |
| client private | `scripts/generate_keypair.py` → `out/` | handed to the client out of band | client signs its `client_assertion` |
| client public | same run, written to `app/keys/client_public.pem` | committed to git, shipped in the zip | warsaw verifies the assertion |
| warsaw signing private | `scripts/generate_keypair.py` → `out/` | SSM SecureString, read at cold start | warsaw signs access tokens |
| warsaw signing public | derived at runtime from the private key | not committed and not deployed; a reference copy is written to `out/` | served at `/.well-known/jwks.json` |

### Why warsaw's public key is derived, not committed

Warsaw's public key is computed from the SSM private key at cold start
(`private_key.public_key()`), rather than shipped as a fourth PEM file.

If it were committed, rotating the SSM parameter without also updating and redeploying the
committed PEM would publish a JWKS that does not match the key tokens are actually signed
with. Every issued token would fail verification, and nothing in CI or at deploy time would
catch it — the failure surfaces only in the client. Deriving the public key makes that state
unrepresentable, and it costs one line.

The generator still writes `out/<name>_public.pem` for both keypairs so the public halves can
be inspected or distributed manually; warsaw's copy is simply informational.

## Module layout

Mirrors helsinki, with `keys.py` and `jwks.py` added and `auth.py` reworked.

| Module | Responsibility | Depends on |
| --- | --- | --- |
| `app/main.py` | `Logger`, `Metrics(namespace="Warsaw")`, `APIGatewayRestResolver`, router registration, cached `init_config()`, `lambda_handler` | all routers |
| `app/clients.py` | cached `get_sqs_client()` | boto3 |
| `app/keys.py` | load and cache the client public key from a configured path; derive warsaw's public key from the config private key; compute RFC 7638 `kid` thumbprints | `cryptography`, `mb_config` |
| `app/auth.py` | `AuthConfig`; `authenticate_client(assertion) -> str` returning the client id, raising a typed error on any failure | `app/keys.py`, `pyjwt` |
| `app/jwt.py` | `JwtConfig`; `jwt_bearer` middleware verifying RS256 bearer tokens against warsaw's derived public key | `app/keys.py`, `pyjwt` |
| `app/oauth.py` | `POST /oauth/token` router; parse the token request, call `authenticate_client`, mint the access token | `app/auth.py`, `app/jwt.py`, `app/keys.py` |
| `app/jwks.py` | `GET /.well-known/jwks.json` router | `app/keys.py` |
| `app/producer.py` | `POST /` router behind `jwt_bearer`; `ProducerConfig`; enqueue to SQS | `app/clients.py`, `app/jwt.py` |

Each config object follows the established pattern: a `BaseModel` with a `section_name`
`ClassVar` and a `@cache`d `get_*_config()` reading from `mb_config.get_config()`.

## Configuration

`app/configs/default.yaml`:

```yaml
producer:
  queue_url: ""

jwt:
  private_key: ""
  issuer: "https://auth.molnarbence.dev/"
  audience: "api://default"
  token_ttl_seconds: 3600
  leeway_seconds: 30

auth:
  allowed_client_id: ""
  client_public_key_path: "app/keys/client_public.pem"
  max_assertion_lifetime_seconds: 300
  leeway_seconds: 30
```

`app/configs/prod.yaml`:

```yaml
ssm_params:
  "string:/projects/warsaw/allowed-client-id": "auth:allowed_client_id"
  "secure:/projects/warsaw/jwt-private-key": "jwt:private_key"
```

`client_public_key_path` is configurable purely so tests can point at a generated key in a
temp directory instead of the committed one. Production never overrides it.

`leeway_seconds` appears in both sections and means the same thing in each: `auth` governs
clock-skew tolerance when validating an incoming client assertion, `jwt` governs it when
`jwt_bearer` validates an access token. They are separate settings because the two have
different threat profiles and may need to diverge; both default to 30.

`expires_in` in the token response is always `jwt.token_ttl_seconds` — the two are never
allowed to drift, so the response builds its value from the config rather than a literal.

The private key is a multi-line PKCS#8 PEM stored in a SecureString parameter; newlines
survive SSM and the `JWT__PRIVATE_KEY` environment override used in tests.

## Endpoints

### `POST /oauth/token`

Accepts `application/x-www-form-urlencoded` (the RFC-normative form) and `application/json`,
reusing helsinki's dual-parser approach — `_get_token_request(body, content_type)` replaces
helsinki's `_get_client_credentials`.

Required parameters:

| Parameter | Required value |
| --- | --- |
| `grant_type` | `client_credentials` |
| `client_assertion_type` | `urn:ietf:params:oauth:client-assertion-type:jwt-bearer` |
| `client_assertion` | the signed JWT |

Assertion validation, in order:

1. `client_assertion_type` matches exactly, else `invalid_request`.
2. Decode with the client public key, `algorithms=["RS256"]` only — the algorithm allowlist is
   what prevents `alg: none` and HMAC-confusion attacks.
3. `aud` equals the configured issuer `https://auth.molnarbence.dev/`. Chosen over the
   generated `execute-api` token endpoint URL, which is unstable across API recreation and
   awkward to bake into a client. Still a valid audience identifier for the AS.
4. `iss` and `sub` both equal `auth.allowed_client_id` (RFC 7523 §3 for a client assertion).
5. `exp` is required and in the future, with `leeway_seconds` of clock skew tolerance.
6. `exp - now <= max_assertion_lifetime_seconds` (300s). Rejects long-lived assertions and
   bounds the window in which a captured assertion is reusable.

Success returns `200` with the helsinki-compatible body shape:

```json
{ "access_token": "...", "token_type": "Bearer", "expires_in": 3600, "scope": "openid" }
```

Access token claims — `iss`, `sub` and `azp` set to the client id, `aud`, `iat`,
`exp = iat + token_ttl_seconds`, `scp: ["openid"]`, and a random `jti`. The JOSE header carries
`alg: RS256` and the `kid` matching the JWKS entry.

### `GET /.well-known/jwks.json`

Returns warsaw's derived public key as a single-entry JWKS. `RSAAlgorithm.to_jwk()` produces
only `{kty, n, e, key_ops}`, so the module adds `kid`, `alg: "RS256"` and `use: "sig"`, and
drops `key_ops` (JWKS convention prefers `use`).

```json
{ "keys": [ { "kty": "RSA", "use": "sig", "alg": "RS256", "kid": "<thumbprint>", "n": "...", "e": "AQAB" } ] }
```

Served with a `Cache-Control: public, max-age=300` header. The endpoint sits behind the same
IP-allowlist resource policy as everything else, which is acceptable — the only consumer is
the same IP-allowlisted client.

### `POST /`

Unchanged from helsinki apart from the middleware's verification key: `jwt_bearer` now
verifies RS256 against warsaw's derived public key instead of HS256 against a shared secret,
and pins `algorithms=["RS256"]`. Empty body → `400`; SQS `ClientError` → `500`;
success → `202`.

## Errors and metrics

`/oauth/token` returns RFC 6749 §5.2 error objects, `{"error": ..., "error_description": ...}`,
because it is an OAuth endpoint and clients are entitled to that shape. Every other route and
the bearer middleware keep helsinki's `{"message": ...}`. `error_description` stays generic —
it never reveals which specific check failed.

| Condition | Status | Body |
| --- | --- | --- |
| missing/unsupported `grant_type` or `client_assertion_type` | 400 | `invalid_request` |
| assertion malformed, badly signed, expired, over-long, or wrong `iss`/`sub`/`aud` | 401 | `invalid_client` |
| bearer token missing, malformed, expired, or invalid on `POST /` | 401 | `{"message": ...}` |
| empty body on `POST /` | 400 | `{"message": ...}` |
| SQS failure | 500 | `{"message": ...}` |

Custom EMF metrics in namespace `"Warsaw"`, following the convention of measuring only the
paths that a caught-and-returned response hides from Lambda's built-in `Errors` metric:

- `ClientAuthFailure`, dimensioned by `reason` ∈ `{BadAssertionType, Malformed, BadSignature,
  Expired, LifetimeTooLong, UnknownClient}` — emitted from `app/oauth.py`.
- `TokenRejected` — emitted from `jwt_bearer` in `app/jwt.py`.
- `EnqueueFailure` — emitted from `app/producer.py`.

The reason dimension is what makes a misconfigured client (`UnknownClient`, `BadSignature`)
distinguishable from a clock-skew problem (`Expired`) without reading logs.

## Helper script

`scripts/generate_keypair.py`, run via `uv run`. `scripts/**` already has `T201` relaxed in
`per-file-ignores`, so it can print guidance.

```
usage: generate_keypair.py --name NAME [--key-size 2048] [--out-dir out]
                           [--public-out PATH] [--force]
```

Behaviour:

- Generates an RSA keypair (default 2048 bits, `public_exponent=65537`).
- Writes the private key as unencrypted PKCS#8 PEM to `<out-dir>/<name>_private.pem` with
  mode `0600`.
- Writes the public key as SPKI PEM to `--public-out`, defaulting to
  `<out-dir>/<name>_public.pem`.
- **Refuses to overwrite an existing file unless `--force`.** Silently clobbering a live
  signing key is unrecoverable, so this guard is not optional.
- Prints the computed `kid` thumbprint and the next manual step for that key.

Two Makefile targets wrap it:

```make
keypair-client:   ## Client keypair: public into the package, private into out/ for the client.
	uv run scripts/generate_keypair.py --name client --public-out app/keys/client_public.pem

keypair-signing:  ## Warsaw token-signing keypair; upload the private half to SSM.
	uv run scripts/generate_keypair.py --name warsaw
```

`out/` is added to `.gitignore`.

### Operational runbook

1. `make keypair-signing`, then upload `out/warsaw_private.pem` to
   `/projects/warsaw/jwt-private-key` as a SecureString. Delete the local copy.
2. `make keypair-client`, commit the updated `app/keys/client_public.pem`, and deliver
   `out/client_private.pem` to the client over a secure channel. Delete the local copy.
3. Set `/projects/warsaw/allowed-client-id` to the agreed client identifier.

## Infrastructure

Three stacks, matching helsinki's set exactly — no `sqs.yml`, no consumer.

| Stack | File | Notes |
| --- | --- | --- |
| resource group | `aws/resource-group.yml` | verbatim from helsinki; tag-based on `Project=warsaw` |
| IAM role | `aws/iam-role.yml` | `sqs:SendMessage` on `/sqs/oslo/queue-arn`; `ssm:GetParameter` on `/projects/warsaw/*`; `kms:Decrypt` on `alias/aws/ssm`; `AWSLambdaBasicExecutionRole` |
| Lambda + API | `template.yaml` | SAM; `AWS::Serverless::Api` with helsinki's IP-allowlist resource policy; `AWS::Serverless::Function` on python3.14, handler `app.main.lambda_handler`, 10s timeout, 128MB |

The queue is consumed as SSM-typed CloudFormation parameters — `/sqs/oslo/queue-url` into the
function's `PRODUCER__QUEUE_URL` environment variable, `/sqs/oslo/queue-arn` into the role
policy — so warsaw never creates or owns queue infrastructure.

Function environment: `POWERTOOLS_SERVICE_NAME`, `POWERTOOLS_LOG_LEVEL=INFO`, `CONFIG_ENV=prod`,
`PRODUCER__QUEUE_URL`. Routes are covered by the existing `ANY /` and `ANY /{proxy+}` events,
so `/oauth/token` and `/.well-known/jwks.json` need no template changes.

`samconfig.toml` is copied unchanged (region `eu-central-1`, bucket `molnarbence-prod-lambda-code`).

## Dependencies

```toml
dependencies = [
    "aws-lambda-powertools>=3.31.0",
    "mb-config[ssm]>=0.2.0",
    "pydantic>=2.13.4",
    "pyjwt[crypto]>=2.13",
]
```

`pyjwt[crypto]` rather than helsinki's bare `pyjwt` is load-bearing. In helsinki, `cryptography`
reaches the environment only as a transitive dev dependency of `moto`; `uv export --no-dev`
confirms it is absent from the production closure. Because helsinki only uses HS256 it never
notices. Warsaw needs `cryptography` for RS256 at runtime, so with a bare `pyjwt` every test
would pass locally while the deployed Lambda raised on the first signing attempt. The extra is
what pulls `cryptography` into the production closure.

`cryptography` ships as a compiled wheel. The existing `install-pip-ci` target already pins
`--python-platform x86_64-manylinux2014 --python 3.14`, so the correct manylinux wheel is
installed for Lambda; no build changes are needed, but the zip grows by roughly 10MB.

The dev group is copied from helsinki unchanged.

## Testing

`tests/` is a package, as in stockholm, so `from app import ...` resolves without installing.
All `@cache`d accessors get `cache_clear()` in an autouse fixture alongside
`mb_config.reset_config()`.

RSA generation is slow enough to matter, so `conftest.py` generates one client keypair and one
warsaw signing keypair at **session** scope and reuses them across every test. The client
public key is written to a session-scoped temp file, and `AUTH__CLIENT_PUBLIC_KEY_PATH` plus
`JWT__PRIVATE_KEY` are set as environment overrides — so no test depends on the committed PEM.

Fixtures: `lambda_context`, `make_event` (REST v1 shape, from helsinki), `make_assertion`
(parameterised over signing key, `iss`, `sub`, `aud`, and lifetime), and `make_token`.

| File | Covers |
| --- | --- |
| `test_keys.py` | key loading and caching; `kid` thumbprint stability; public key derived from private matches the generated public |
| `test_committed_client_key.py` | the committed `app/keys/client_public.pem` exists and parses as an RSA public key — guards against a corrupt or missing file reaching the zip |
| `test_auth.py` | every assertion rejection path: wrong signer, wrong `iss`, wrong `sub`, wrong `aud`, expired, no `exp`, lifetime over 300s, `alg: none`, HS256-signed |
| `test_oauth.py` | body parsing in both content types; wrong `grant_type`/`client_assertion_type`; RFC 6749 error shapes; issued token claims and `kid` header |
| `test_jwks.py` | JWKS structure; `kid` matches the token header; a token verifies against the published JWK |
| `test_jwt.py` | `jwt_bearer` accept and reject paths, including a token signed by the client key rather than warsaw's |
| `test_producer.py` | enqueue via moto with a real queue; empty body; SQS failure |
| `test_clients.py`, `test_main.py`, `test_prod_config.py` | as helsinki, with warsaw's SSM parameter paths |

The end-to-end case worth naming explicitly: mint a token through `POST /oauth/token`, then
present it to `POST /` and assert a `202` — that is the only test that proves the signing key
and the middleware's verification key are the same key.

Coverage gate stays at `fail_under = 75`.

## CI

`.github/workflows/main.yaml` copied from helsinki with `PROJECT_NAME: warsaw`. Jobs: sonarqube
(lint + coverage + scan), build-lambda-zip, cfn-lint, then on push to `main` only,
deploy-resource-group → deploy-iam-role → deploy-lambda via `sam deploy`. Deploys use OIDC
(`DEPLOY_ROLE_ARN`) into `eu-central-1`. `sonar-project.properties` uses projectKey
`mb-dot-dev_warsaw-self-signed-rest-api`. `dependabot.yml` copied unchanged.

The `prepare` job's unused `jwt_issuer`/`jwt_audience` outputs, which helsinki declares but
never populates, are dropped.

## Risks

- **Key/parameter mismatch on first deploy.** If `/projects/warsaw/jwt-private-key` is unset or
  malformed, every request fails at cold start. The runbook ordering above puts SSM setup
  before the first deploy.
- **Clock skew.** A client with a fast clock produces assertions whose `exp` exceeds the 300s
  cap, or whose `iat` is in the future. `leeway_seconds: 30` absorbs normal drift; the
  `Expired` metric reason makes the pathological case visible.
- **No replay protection.** A captured assertion is reusable within its remaining lifetime
  (≤300s) from an allowlisted IP. Accepted: single client, IP-gated API, TLS in transit. If
  this becomes unacceptable, add a DynamoDB `jti` table with TTL — the validation function is
  already the single choke point where that check would go.
